# Formal claims register (kit)

This page describes a second register of what Averin's formal and test evidence covers,
checked by a script (the register is checked, not the claims in it). The kit's default command, `python3 scripts/formal/check_claims.py` with no arguments, fails here by design because it reads the legacy `formal/claims.json`; use `--claims formal/kit-claims.json` or `make formal-kit`. It does not replace `formal/README.md` (the evidence itself) or
`formal/claims.json` (the full inventory, checked by `scripts/check-claims.py`). It adds
three things the inventory does not have: a drift lock on the code each claim protects,
a mutant that shows each detector can fail, and a denylist of overclaim phrases.

## What the register is

`formal/kit-claims.json` is read by the shared kit vendored in `scripts/formal/`
(`check_claims.py`, `check_mutants.py`, `formal_kit.py`; byte-identical to the kit, do not
edit them here). Each claim carries:

- `statement`: one bounded sentence about what the detector checks.
- `method`: one of the kit's methods (`scripts/formal/README.md`); this register uses lean, kani,
  tla, differential-vectors, exhaustive, fuzz, property and test.
- `gates`: CI job ids that run the evidence on pull requests or on the schedule.
- `detector`: a shell command, run from the repo root, that passes on the real tree.
- `detector_kind`: `custom` on every claim (and every mutant with its own detector) whose detector
  is not a cargo or go test (Kani, Lean, TLC, the production call-path script). The kit's
  vacuity guard cannot read such output, so those detectors must fail by themselves when nothing
  was checked (`run-kani.sh` requires a complete successful harness section, `run-tlc.sh` pins the
  checked names, the Lean detector builds with warnings as errors and audits axioms).
- `covers`: the exact functions the claim protects, each with a sha256 (the drift lock).
- `mutants`: ids of patches in `formal/mutants/`; the detector must fail on each one.
- `does_not_establish`: what the claim leaves open.

The two registers are linked: every kit claim names the claim in `formal/claims.json` it
backs in its `$comment` ("legacy register: <id>"), and `scripts/check-claims.py` fails if
that id does not exist. Kit statements are narrower than the legacy ones on purpose: a kit
claim says what its cheap detector checks, not what the whole proof program shows.

## How to add a claim

1. Write the proof or test and make a CI job run it.
2. Add the claim to `formal/kit-claims.json` with `"sha256": ""` in each cover.
3. Write a mutant: change the covered code so the claim should be false, then
   `git diff -- <covered file> > formal/mutants/<id>.patch` and `git checkout -- <covered file>`.
   The patch must apply with `git apply` (the legacy suite uses `patch`, which is more lenient,
   so check a reused legacy patch with `git apply --check` first).
4. Add the id to the `mutants` map with a `tier` (`fast` or `full`). Mutants that only the kit
   register runs must be named `lean-*`, `tla-*`, `seal-skips-*`, `surface-*` or `multiwriter-*`; the legacy
   `formal/check-mutants.sh` skips those names, since it only knows its own gates (any other name
   is applied there too and must die to one of them).
5. `python3 scripts/formal/check_claims.py --claims formal/kit-claims.json --relock --symbol <path>:<symbol>`
   fills the empty hashes.
6. Commit, then `python3 scripts/formal/check_mutants.py --claims formal/kit-claims.json --only <id>`
   must report `killed` (it tests HEAD, not the working tree).
7. Say plainly in `does_not_establish` what remains open.

The Aeneas production-proof mutants (m50, m54 to m58, and m60 to m64 as proof mutants) run in the
legacy suite on every pull request (`formal-production`), not here, because the Aeneas toolchain is not
set up for the kit. m61 to m64 are also killed by the native parser tests, so they are in this
register under `parser-differential-and-fuzz` (m63 edits `parse_value`, which that claim now
covers). m60 survives the native fuzz and differential tests (they only pass valid UTF-8 strings);
only the totality proof kills it, so it is not in this register. m43 (temporal) is registered under
`temporal-revocation-ordering-tests`. The Kani mutants m2, m3 and m12 are registered under
`kani-canon-harnesses` and m4 and m9 to m11 under `kani-encoder-harnesses`; m42 and the Kani mutants
m13 and m22 to m25 are not registered and stay in the legacy suite.

## Drift lock and relock policy

A hash mismatch means a covered function changed after the claim was written. Re-read the
claim, decide it still holds (or downgrade or remove it), then relock only the symbols you
changed on purpose with `--relock --symbol path:symbol`. Never relock everything to turn CI
green. The PR text names every relocked symbol and why. A drift lock says the text is unchanged,
not that the claim is still true: a callee can change without changing the hash.

## Mutants and tiers

`check_mutants.py` makes a scratch worktree at HEAD, applies each mutant, runs the detector and
requires it to fail. A mutant that does not change a covered symbol is reported as a vacuous
kill, not a kill. Before any mutant, each detector runs once on the unmutated tree and must pass;
a cargo test detector whose name filter matched no test fails there as vacuous (kit v2), so a
renamed test cannot leave a filtered detector passing with nothing checked. The guard shows that
at least one test ran, not that every named test did. The scratch tree is restored after every
run; `formal/lean/.lake` is kept between runs (`scratch_cache_dirs`) so the Lean detector does
not rebuild from nothing for each mutant. Fast-tier mutants (one per claim that has a native
detector) run in the `formal-fast` job on every pull request, which `ci-required` needs. All
mutants, including the Kani, Lean and TLA+ ones, run in `formal-nightly` (schedule and manual
dispatch only), which uploads a JSON report as an artifact kept 90 days. To run it on a branch
without the 68 Kani string family slices, dispatch ci with
`gh workflow run ci.yml --ref <branch> -f scope=kit-nightly`. The older suite
(`formal/check-mutants.sh`, `formal-mutants-fast`, `formal-mutants-full`) is unchanged and still
runs.

The kit marks a kill whose output looks like a build failure with a WARNING. Every Lean kill does,
because a Lean proof that no longer checks is a build error. Each Lean mutant here changes a
theorem statement and keeps the proof script (one weakens the format hypothesis `hfmt` to
`fmt x = fmt y -> True`, one drops the SHA-256 collision alternative from the conclusion), so the
kill is the proof failing to check (type mismatches), not a syntax error or a missing name. The
first full run of every kit mutant on GitHub, including the Kani mutants m2, m3, m11 and m12, is
CI run 37865103811 (`formal-nightly`, 55 of 55 killed), recorded as each claim's `evidence_run`.
`lean-seal-drops-fmt-injectivity` was rewritten after that run: it used to delete `hfmt`, so the
proof failed on an unknown name rather than on the missing injectivity.

## Overclaim denylist

`overclaim_denylist` lists phrases the README and `docs/` must not contain (wording that
claims whole-system or complete verification; the list is in the JSON file). The legacy checker's sentence rules stay in force too.
Matching ignores case and line breaks.

## Evidence of record

Only a CI run counts as evidence for a claim. Local runs of the detectors or mutants are
informative only. The kit does not fetch run ids; `evidence_run` is optional.
